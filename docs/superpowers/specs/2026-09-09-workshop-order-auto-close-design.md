# 车间订单自动结案设计

## 目标

车间订单的出库数量达到订单数量后开始计时，满 2 天自动从“生产中”改为“已结案”。现有的手动结案、反结案权限和页面入口保持不变；订单一旦被手动反结案，后续永久退出自动结案流程。

本次还要按同一口径处理现有订单：根据当前物料转移记录推导首次达到 100% 的时间，立即结案已经满 2 天的订单，未满 2 天的继续等待。

## 当前口径与现状

- 订单表：`public.sales_orders`
- 订单数量：`sales_orders.order_quantity`
- 订单状态：`sales_orders.status`，取值为“生产中”或“已结案”
- 结案时间：`sales_orders.closed_at`
- 出库数量：同一项目号下 `public.material_transfers.transfer_quantity` 的合计
- 页面当前依据：`totalOutbound >= orderQuantity` 即完成度达到 100%
- 当前项目号没有重复，现有聚合口径可以唯一关联订单
- 调查时共有 466 个生产中订单达到 100%，其中 446 个推导出的达标时间已满 2 天，20 个尚在等待期

## 方案选择

采用 PostgreSQL 触发器配合 Supabase Cron（`pg_cron`）的数据库原生方案。

未采用的方案：

- 只靠页面打开时检查：无人访问页面时不会执行，不符合自动化要求。
- 只靠定时任务反推达标时间：当历史转移单被编辑时，无法准确区分“原本早已达标”和“刚刚因编辑而达标”。
- 定时调用 Edge Function：需要额外部署、鉴权和网络调用，本规则完全可以在数据库内完成。

## 数据模型

在 `public.sales_orders` 增加两个字段：

- `completion_reached_at timestamptz null`：订单当前这一次达到 100% 的时间。跌破 100% 时清空，再次达到时重新计时。
- `auto_close_disabled boolean not null default false`：是否永久退出自动结案。只有“已结案 → 生产中”的反结案转换会把它设为 `true`，之后不再自动恢复。

字段不新增页面展示，也不改变现有表单、筛选、导入导出字段。

## 状态规则

| 当前情况 | 数据动作 | 后续行为 |
| --- | --- | --- |
| 生产中，出库不足 100% | `completion_reached_at = null` | 不自动结案 |
| 生产中，首次达到 100% | 写入当前时间 | 开始 2 天等待期 |
| 生产中，已达到 100% 但未满 2 天 | 保留达标时间 | 继续等待 |
| 生产中，达到 100% 已满 2 天，且未禁用自动结案 | 状态改为“已结案” | 由现有触发器写入 `closed_at` |
| 已结案，被手动改回生产中 | `auto_close_disabled = true` | 永久不再自动结案 |
| 已禁用自动结案的订单再次达到 100% | 可维护完成达标时间，但不改状态 | 仅允许用户手动结案 |
| 用户手动结案 | 保持现有权限与流程 | 正常写入 `closed_at` |

“反结案”通过数据库状态转换识别，因此现有单条编辑、详情操作和批量操作都遵循相同规则，不依赖某一个前端入口。

## 数据库实现

1. 新建一个按项目号刷新、计算订单当前完成度的数据库函数。
2. 在物料转移单新增、修改数量或项目号、删除后，刷新受影响订单的 `completion_reached_at`。
3. 在订单新增或修改项目号、订单数量后，也刷新该订单的达标时间。
4. 扩展订单状态触发器：检测“已结案 → 生产中”，将 `auto_close_disabled` 置为 `true`；原有 `closed_at` 行为保持不变。
5. 启用 `pg_cron`，通过 `cron.schedule` 注册有稳定名称的任务，每 15 分钟执行一次自动结案函数。迁移重复执行时先按任务名取消旧任务，避免重复注册；不直接修改 `cron.job`。
6. 自动结案函数只更新同时满足以下条件的订单：
   - 状态为“生产中”
   - `auto_close_disabled = false`
   - 当前出库数量仍达到订单数量
   - `completion_reached_at <= now() - interval '2 days'`

## 存量数据处理

迁移内按物料转移记录的 `created_at, id` 顺序计算项目号累计出库量，取累计数量首次达到订单数量的时间回填 `completion_reached_at`。

然后立即调用一次自动结案函数：

- 已满 2 天的现有订单立即结案；
- 未满 2 天的订单保留为生产中，等待定时任务；
- 当前未达到 100% 的订单不处理；
- 已结案订单不改动；
- 因系统此前没有反结案历史标志，现存生产中订单按用户要求统一重新判断，不追溯豁免。

## 权限与安全

- 不调整 `feature:workshop-order.manage-status` 或任何页面权限。
- 前端用户仍通过现有 RLS 和权限入口手动结案/反结案。
- 定时任务只调用无参数的内部数据库函数；不给 `anon` 或 `authenticated` 新增函数执行权限。
- 使用 `cron.schedule` 管理任务，符合 Supabase Cron 当前要求。

## 验证方案

1. 迁移执行成功，`pg_cron` 已启用且任务只注册一份。
2. 重新生成 `src/services/database.types.ts`，确保新增字段进入自动生成类型。
3. 数据查询验证存量订单：已满 2 天的达标生产中订单为 0，未满 2 天的订单仍保持生产中。
4. 在事务内构造并回滚测试数据，覆盖：不足 100%、刚达到 100%、跌破后清空、满 2 天自动结案、反结案后不再自动结案。
5. 运行相关单测、`bun run test`、`bun run typecheck` 和 `bun run build`。
6. 在订单管理页面人工检查生产中/已结案页签、手动结案和反结案入口仍按原权限显示与刷新。

## 边界与回滚

- 定时任务每 15 分钟运行，因此实际结案时间最多比满 2 天晚约 15 分钟。
- 物料转移单若被修改导致完成度跌破 100%，达标时间会清空；恢复到 100% 后重新计算 2 天。
- 回滚时需先按任务名调用 `cron.unschedule`，再移除新增触发器、函数和字段；现有已自动结案的数据不会自动反结案。
